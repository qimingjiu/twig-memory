# 衔枝 Twig · 让 AI 记住你，而不是只记住话

> 你的 AI 聊了三天像失忆？用户觉得 AI 根本不懂他？
> **衔枝是一个叙事记忆引擎。接上去，AI 会越长越懂人。**

它不是把聊天记录存成一堆卡片，等用的时候按关键词检索。它让 AI 持续形成对人的理解，并在每次对话前把「我对你的理解」注入上下文——像一本还在续写的书，而不是一盒散落的卡片。

衔枝面向所有长程 agent：陪伴 AI、教育 AI、医疗陪护、NPC、个人助理。它解决的核心问题是：**怎么让 AI 在长程关系里不失忆、不跑偏、不被自己的偏见带偏。**

## 一分钟跑起来

**你想做什么？**

- **自己用 / 先看看「记忆书」** → 跟完本节四步，浏览器里翻开它
- **接进手机 App / AI 客户端**（RikkaHub / Kelivo / Operit 等）→ 用[远程 MCP](server/README.md)，手机上什么都不用装
- **开发者接 API / 跑评测** → [server/README.md](server/README.md) 完整文档
- **装不上？** 把 [docs/DEPLOY-FOR-AI.md](docs/DEPLOY-FOR-AI.md) 整个发给你的 AI，说一句「照这个带我装」

### 1. 克隆并安装

```bash
git clone https://github.com/qimingjiu/twig-memory.git
cd twig-memory
npm install
```

需要 Node.js 22 或更新（底线 20.19；`node -v` 看一眼）。

### 2. 配置 LLM Key（可选，但推荐）

```bash
# 新建 .env.local（已被 .gitignore 排除）
KIMI_API_KEY=sk-你的-Moonshot-API-Key
```

不配也能跑：引擎自动回退规则判定，基础功能照常。但反刍、盲推导审计、日记与便签生成这些标注「需 key」的 LLM 功能会不可用——想见到完整的衔枝，建议配上。

### 3. 启动服务端

```bash
npm run server:http   # HTTP API + 远程 MCP，默认 http://localhost:7300
```

### 4. 打开记忆书（另开一个终端）

```bash
npm run dev   # 记忆书前端，默认 http://localhost:7100
```

浏览器打开 **http://localhost:7100** ——今日扉页 / 记忆书 / 故事线 / 理解文档 / 自检日志 / 设置，都在这本「书」里。

刚翻开时书是空的，正常：**记忆书是引擎的展示窗**，记忆来自你接上去的 AI。客户端挂上[远程 MCP](server/README.md) 后正常聊天，事件就会流进引擎，日记、心迹、便签、印章才会一天天长出来。开发者也可以直接把事件 POST 到 `/v1/ingest`、每次回复前 GET `/v1/context` 注入 system prompt。

> 完整 API 文档、MCP 挂载方式、Zeabur 一键部署见 [server/README.md](server/README.md)。

## 接入后，你的 AI 会拿到什么？

每次对话前，衔枝返回的不是 top-k 条相似聊天记录，而是一个**叙事上下文包**：

```json
{
  "threads": [
    { "label": "攒钱买硬盘", "openQuestion": "设备层面的创作限制是否解除？" }
  ],
  "claims": [
    { "text": "她用创作来重建掌控感，尤其在压力大的时候", "conviction": 0.82 }
  ],
  "recentFragments": [
    { "date": "8月4日", "title": "出道直播排练" }
  ],
  "promptText": "可直接注入 system prompt 的叙事文本"
}
```

**什么意思？** 你的 AI 不会只得到「用户上周说过想换电脑」，而是会得到：

> 用户正在攒钱买硬盘，这个问题还没闭环。她之前因为旧电脑丢稿焦虑过，最近提到新设备可能让她创作更顺。目前对她的理解是：她会把创作当作压力出口，但不要替她下诊断。

**这和 top-k 检索的区别：**

| top-k 检索 | 衔枝的叙事上下文包 |
|---|---|
| 给你 5 条最像的聊天记录 | 给你「这件事发展到了哪一步」「我对用户的当前理解是什么」 |
| 需要 LLM 自己从碎片里悟 | 已经帮你把线索和判断织好了 |
| 旧话题容易被遗忘 | 未闭合的线索会持续跟踪，直到回收或归档 |

## 它怎么做到的？

衔枝把记忆分成三层来织：

```
┌─ 认识层 ── 对「这个人」的活文档（改写式更新，有版本史）
├─ 线索层 ── 未闭合的问题（不是事件本身，而是事件指向的悬念）
└─ 碎片层 ── 原始事件（带情感坐标，情绪越强的记忆衰减越慢）
```

**一个例子：**

用户三天前说「我想攒钱买硬盘」，昨天说「旧电脑又卡了」，今天说「终于下单了」。

- 碎片层：记下三条事件。
- 线索层：把「攒钱买硬盘」登记为一个未闭合问题，持续跟踪它有没有被解决。
- 认识层：当事件足够时，形成「她对创作设备的瓶颈很敏感，升级设备后会明显提升创作信心」的理解——并锚定到具体碎片，不是凭空生成。

更多机制细节（反证搜索、盲推导审计、对照窗口、危机协议）见 [docs/雾尼Muninn-技术设计文档-v1.3.md](docs/雾尼Muninn-技术设计文档-v1.3.md)。

## 这和你用过的记忆库有什么不同？

| 系统 | 它给你 | 衔枝给你 |
|---|---|---|
| mem0 / Zep / Letta | 事实库、向量检索 top-k | 叙事上下文包：线索 + 对人的理解 + 证据 |
| 通用 RAG | 相关片段 | 已经组织好的「故事进展到哪了」 |
| Generative Agents | 追加式洞察（只变长不会变） | 改写式活文档 + 漂移审计 |

## 当前进展

- **服务端接入层**：无头引擎 `HeadlessMuninn`、JSON 持久化、HTTP API、MCP server（stdio + 远程）双接入。
- **新前端「记忆书」已上线**：今日扉页 / 记忆书（日历网格 + 日卡导出）/ 故事线 / 理解文档 / 自检日志 / 设置页（引擎状态灯、存储占用、最近审计一览）。
- **情感层三件套**：日记 / 心迹 / 便签——平行于编织层、只读于引擎；用户回应经影子碎片 + ContextAnchor 进入引擎视野，不污染编织。
- **印章与玻璃珠**：8 章 × 12 珠的火漆封存仪式（`shared/stamps.ts` 前后端共用注册表），一签一章，盖印生成影子碎片让引擎知道今天的心境。
- **冲突响应评测**：22/22（100%）。
- **LoCoMo 事实底盘**：0.640，双口径过线，高于 mem0 参照宏平均。
- **LongMemEval-S**：Overall 0.856 / Task-averaged 0.844 / Abstention 0.867。

完整评测配置与细节见 [server/README.md](server/README.md)；前端与情感层设计见 [docs/新前端技术设计文档-v1.0.md](docs/新前端技术设计文档-v1.0.md)。
